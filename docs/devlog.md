## 2026-11-24 — 기획부터 첫 래더 생성까지

### 한 일

- 아이디어("공정과 I/O 할당표를 주면 래더를 자동 작성")를 PRD와 시스템 설계로 정리 (`PRD.md`)
- 9단계 작업 계획 수립 (`docs/plan.md`)
- M0~M2 구현: 앱 뼈대, GX Works2 CSV 내보내기, 순차 공정 래더 생성, 검증
- 생성한 CSV를 GX Works2(Q03UDV)에 불러와 변환과 코멘트 표시 확인 (사용자가 직접 확인)

### 결정과 이유

**LLM은 공정 해석에만 쓴다**
- 문제: LLM이 래더를 직접 쓰면 같은 입력에도 결과가 달라지고, 틀린 주소나 이중 코일을 막기 어렵다
- 결정: LLM은 "공정 설명 → 단계 표(JSON)"까지만 맡고, 단계 표에서 래더를 만드는 부분은 규칙 기반 코드로 한다
- 결과: 같은 단계 표면 파일이 바이트 단위로 같다 (테스트로 고정)

**단계 릴레이 방식 + 블록 분리**
- 문제 1: 한 출력을 여러 단계가 켜면 이중 코일이 생긴다
- 결정 1: 출력 코일은 프로그램 끝에 출력당 한 렁만 두고, 그 출력을 켜는 단계들을 OR로 묶는다
- 문제 2: 전이 조건이 연속으로 참이면 한 스캔에 여러 단계를 건너뛴다
- 결정 2: "전이 판정"과 "단계 갱신"을 다른 블록으로 나눈다. 판정 블록은 단계 릴레이를 바꾸지 않는다
- 결과: 모든 입력을 켜 둔 상태에서도 스캔마다 한 단계씩만 진행 (테스트로 확인)

**CSV 형식은 추측하지 않고 샘플로 확정**
- 문제: GX Works2 프로그램 CSV의 인코딩, 구분자, 스텝 번호 규칙을 문서 없이 맞춰야 했다
- 결정: GX Works2에서 직접 내보낸 샘플을 받아 그대로 재현하는 바이트 일치 테스트부터 작성
- 알게 된 것
  - 프로그램 CSV: UTF-16 LE + BOM, 탭 구분, CRLF
  - 코멘트 CSV: 같은 인코딩인데 줄바꿈만 LF
  - 피연산자가 둘인 명령(MOV, OUT T, 비교)은 둘째 피연산자를 다음 행에 쓴다
  - 스텝 수: 접점·코일·SET·RST·ORB·ANB 1, MOV·PLS 2, 비교 접점 3, 타이머·카운터 OUT 4
  - D 비트(D0.0)와 SM400을 쓴 접점·코일도 1스텝
- 결과: 샘플 3종과 바이트 일치, GX Works2 불러오기와 변환 오류 없음
- 결과: 생성한 실린더 순차 왕복과 신호등 래더가 GX Works2 시뮬레이터에서 공정대로 동작 (사용자 확인)

**분기 명령(MPS/MRD/MPP)을 쓰지 않는다**
- 문제: 샘플에 없는 명령은 형식을 확인할 수 없다
- 결정: 한 렁의 조건은 하나로 두고 출력을 이어 쓰는 구조로 생성해 분기 명령이 필요 없게 했다

**위험이 큰 부분부터 만든다**
- 결정: 화면보다 먼저 "생성 → CSV → GX Works2 불러오기"를 끝까지 뚫고, 사용자 확인을 통과해야 다음 단계로 간다
- 이유: 불러오기 형식이 틀리면 그 위에 쌓은 것을 전부 고쳐야 한다

**테스트 전용 스캔 해석기**
- 문제: 생성된 래더가 공정대로 도는지 GX Works2 없이는 확인할 수 없었다
- 결정: 명령어 리스트를 스캔 단위로 실행하는 작은 해석기를 테스트에만 둔다 (`tests/sim.ts`)
- 결과: 실린더 순차 왕복(A+ B+ B- A-), 신호등 3사이클을 자동 테스트로 확인

**동작 확인에 PlcTwin을 쓴다**
- 배경: 직접 만든 MPS 디지털 트윈(PlcTwin)이 GX Simulator2와 MX Component로 연동된다
- 결정: 생성한 래더로 3D 설비가 끝까지 도는지를 성공 기준에 추가
- 따라온 변경: I/O 주소에 D 워드 비트 허용, 단계에서 고정값 쓰기(서보 목표 위치), 상시 출력

**코멘트는 쉬운 말, 최대 3행**
- 사용자 요청으로 "전이1 성립" 같은 표현을 "A전진 / 다음은 / B전진"으로 바꿈

### 숫자

- 자동 테스트 13개 통과 (바이트 일치 3, 동작 3, 조건식·분기 2, 검증·구조 검사 2, 코멘트 1, 결정성 1, 샘플 생성 1)

### 아직 안 된 것

- 운전 모드(비상정지, 수동, 원점복귀, 이상 감지), 병렬 분기, 카운터
- 화면 전체, 할당표 읽기, LLM 공정 해석
- PlcTwin 연동과 MPS 라인 공정

## 2026-11-24 — M3: 운전 모드, 병렬 분기, 카운터

### 한 일

- 운전 설정(정지, 비상정지, 리셋, 자동·수동, 원점복귀, 수동 버튼, 인터록 쌍, 센서 쌍, 이상 램프)을 래더로 생성
- 단계 제한 시간과 센서 쌍으로 이상 감지, 이상 번호를 D에 기록
- 카운터, B접점 입력 반전, 병렬 분기·합류
- 검증 추가: 인터록 누락, 갈 수 없는 단계, 합류 없는 병렬 분기
- 기준 공정 "컨베이어 분류", "두 실린더 동시 동작" 추가 (주소·시간은 테스트용 가정값)

### 결정과 이유

**"자동 운전 중" 비트를 따로 둔다**
- 문제: 시작·원점복귀·정지 예약 렁마다 모든 단계 릴레이를 나열해야 했다
- 결정: 프로그램 맨 위에서 단계 릴레이를 OR로 묶어 비트 하나로 만들고 나머지 렁은 그 비트만 본다
- 따라온 변경: M2 때 GX Works2에서 확인한 실린더·신호등 CSV에도 이 렁이 추가되어 파일이 달라졌다. 다시 확인이 필요하다

**정지 예약과 원점복귀는 자기 유지 회로(OUT)로 만든다**
- 이유: SET/RST로 만들면 비상정지 때 원점복귀 비트가 남아, 비상정지를 풀자마자 다시 움직인다. 자기 유지 회로는 조건이 깨지면 바로 풀린다

**이상 번호는 "이상 비트가 꺼져 있을 때만" 적는다**
- 결정: 이상마다 렁 하나에 `MOV 번호` 다음 `SET 이상`을 이어 쓴다. 같은 스캔에 두 이상이 나도 앞 렁이 이긴다
- 결과: 제한 시간 초과(번호 2) 뒤에 센서 모순이 나도 번호가 2로 남는다 (테스트로 확인)

**인터록은 상대 출력 코일의 B접점으로 건다**
- 결과: 수동에서 두 버튼을 함께 누르면 렁 순서가 앞선 출력만 켜진다. 둘 다 꺼지는 방식은 아니다

**합류 없는 병렬 분기는 단계 조합을 따라가 보며 찾는다**
- 결정: 조건을 무시하고 전이를 전부 따라가며 동시에 켜질 수 있는 단계 조합을 구한다. 분기 뒤에 합류 전이가 한 번도 성립하지 못하거나, 이미 켜진 단계를 다시 켜면 오류
- 한계: 조합이 5000개를 넘으면 검사를 멈춘다

**RST C0는 내보내지 않는다 (샘플 대기)**
- 문제: 카운터를 지우는 `RST C0`가 GX Works2 샘플에 없어 스텝 수를 알 수 없다
- 결정: 추측하지 않고, 이 명령이 든 프로그램은 CSV 내보내기에서 오류를 낸다. 생성과 동작 테스트는 한다
- 결과: 컨베이어 분류는 동작 테스트만 통과, CSV는 아직 없음

**(같은 날 추가) RST C0 샘플 수령**
- 사용자가 GX Works2에서 내보낸 샘플로 확인: `RST C0` 4스텝, `BKRST M100 K20` 3스텝, `LDP X3` 2스텝, `FMOV K2 D100 K5` 4스텝
- 결과: 샘플과 바이트 일치(`tests/fixtures/MAIN_rstc.csv`), 내보내기 차단을 RST C에 한해 해제, 컨베이어 분류 CSV 생성. SET C와 SET/RST T는 여전히 차단
- BKRST는 "모든 단계 해제" 렁에 쓴다: 단계 릴레이가 연속 번호라 `RST` 나열 대신 `BKRST M0 K단계수` 한 줄 (사용자 제안). 카운터는 BKRST 샘플이 없어 `RST C`를 그대로 쓴다
- LDP·FMOV는 스텝 수만 반영했다. FMOV는 같은 값을 연속 워드에 쓰는 명령인데 지금은 그런 곳이 없다 (이상 번호는 워드 1개)
- 자동 테스트 27개 통과

**(같은 날 추가) 범위 확장: 워드 계산과 비교**
- 배경: PRD는 데이터 연산을 범위 밖으로 두었으나 사용자가 넓히기로 결정
- 결정: 16비트 워드의 사칙연산·대입(단계의 `calcs`)과 비교 조건(`compare`)만 넣는다. 32비트, 실수, 계산식 중첩은 계속 범위 밖
- 결정: 계산은 단계에 들어올 때 한 번만. 펄스 명령(`+P` 등)을 단계 릴레이에 걸면 켜지는 순간에만 실행되어 추가 접점이 필요 없다
- 결정: 계산·비교에 쓰는 워드는 단계 표의 `data`에 선언한 것만 허용 (주지 않은 주소를 만들지 않는다는 원칙)
- 알게 된 것: Q 시리즈 곱셈은 결과가 32비트라 다음 워드까지 쓰고, 나눗셈은 나머지를 다음 워드에 쓴다. 다음 워드가 다른 용도와 겹치면 구조 검사에서 오류로 잡는다 (명령 동작은 샘플이 아니라 사전 지식이므로 GX Works2 시뮬레이터에서 확인 필요)
- 결정: 스텝 수 표에 없는 명령은 내보내기에서 전부 오류. 전에는 모르는 명령을 1스텝으로 계산했다
- 결과: 동작 테스트 통과, 계산이 든 공정의 CSV 내보내기는 샘플 수령 전까지 차단
- 자동 테스트 30개 통과

**(같은 날 추가) 계산 샘플 수령**
- 확인한 스텝 수: MOVP 3, DMOV 3, BMOV 4, 비교 접점 6종 3, `-P D10 D11 D12` 4, `*P D10 K2 D20` 4, `/P D20 K3 D22` 4
- 문제: `+P D10 K1 D10`만 5스텝이었다. `+P`라서인지, 첫 값과 대상이 같은 워드라서인지 샘플 하나로는 알 수 없다
- 결정: 샘플에 있는 모양만 내보낸다 (`+P`는 첫 값 = 대상일 때 5, 나머지 셋은 세 값이 모두 다를 때 4). 그 밖의 모양은 오류. 원인을 가르는 샘플을 추가로 받는다
- 결과: 샘플과 바이트 일치(`tests/fixtures/MAIN_calc.csv`), 자동 테스트 31개 통과

**(같은 날 추가) 사칙연산 스텝 수 규칙 확정**
- 두 번째 샘플: `+P D10 K1 D12` 4, `-P D10 K1 D10` 5, `*P D10 K2 D10` 4, `/P D10 K2 D10` 4, `+P K1 D10 D10` 4, `+P D10 D10 D12` 4
- 알게 된 것: 덧셈·뺄셈은 첫 값과 대상이 같은 워드일 때만 5스텝, 그 밖에는 4스텝. 곱셈·나눗셈은 같아도 4스텝. 둘째 값이 대상과 같은 것은 영향이 없다
- 남은 가정: 첫 값 = 대상이면서 둘째 값이 워드인 모양(`+P D10 D11 D10`)은 샘플이 없고 5스텝으로 본다
- 결과: 샘플과 바이트 일치(`tests/fixtures/MAIN_calc2.csv`), 계산 내보내기 차단 해제, 자동 테스트 32개 통과

## 2026-11-24 — M3-T: PlcTwin 연동과 MPS 라인

### 한 일

- 할당표 주소에 D 비트(D0.F)와 D 워드(D144) 허용
- 단계의 값 쓰기(`writes`), 운전 설정의 상시 출력(`alwaysOn`)과 상시 값(`alwaysWrites`). 상시 ON 접점은 SM400
- 검증 추가: 입력 주소에 쓰는 명령, 내부 디바이스와 할당표 주소의 겹침 (이상 번호 D0과 PlcTwin 입력 D0.x가 겹치는 경우 등)
- MPS 라인 공정을 단계 20개, 전이 21개로 작성하고 CSV 생성 (`samples/mps/`)

### 결정과 이유

**공정 순서를 PRD와 다르게 잡았다**
- 문제: PRD는 "송출 → 컨베이어 → 스토퍼·판별 → 가공"으로 적었으나, PlcTwin 설비 모델에서 드릴은 공급 실린더가 칩을 밀어 놓는 작업대 위에 있고 판별 센서는 스토퍼보다 앞에 있다
- 결정: 공급 → 가공 → 송출 → 컨베이어 → 판별 → (금속) 스토퍼 정지·리프트·창고 적재 / (비금속) 배출

**서보 이동 단계를 연달아 두지 않는다**
- 문제: PlcTwin의 위치완료(D3.4)는 "이동 명령 ON이고 현재 위치 = 목표"일 때 켜진다. 이동 단계 두 개가 붙어 있으면 목표만 바뀌고 이동 명령은 켜진 채라, 앞 단계의 위치완료가 통신 주기 동안 남아 다음 단계를 바로 통과시킬 수 있다
- 결정: 하강과 상승 사이에 칩잡기 단계(이동 명령 OFF)가 들어가도록 단계를 나눴다

**비금속 배출 위치는 타이머로 맞춘다**
- 문제: 배출 실린더 앞에는 칩을 세우는 센서나 스토퍼가 없다
- 결정: 물품감지 후 1.6초 뒤 컨베이어를 세우고 민다. 거리 약 180 mm, 벨트 100 mm/s에서 통신 지연을 뺀 값이고, 배출 실린더가 칩을 잡는 범위는 ±30 mm
- 한계: 통신 주기에 따라 어긋날 수 있다. PlcTwin에서 보고 조정할 값이다

**sim 테스트용 설비는 순서만 본다**
- 결정: 테스트 안에 실린더·벨트·리프트·흡착을 흉내 내는 작은 설비를 두었다. 실린더는 즉시 끝에 닿고 통신 지연이 없다
- 결과: 금속 칩은 선반, 비금속 칩은 배출 상자에 도착하고 단계 순서가 기대와 같다. 실제 타이밍은 PlcTwin에서만 확인된다

### 결정과 이유

**xlsx 라이브러리는 read-excel-file**
- 후보: npm의 `xlsx`(SheetJS)는 0.18.5에서 멈춰 있고 최신판은 npm이 아닌 곳에서 배포된다. `read-excel-file`은 9.3.20으로 2026-11-19에 갱신됐고 읽기 전용이라 작다
- 결정: `read-excel-file`의 `readSheet`(Node용)로 첫 시트만 읽는다

**CSV는 CP949도 읽는다**
- 이유: 한글 Excel에서 "CSV(쉼표로 분리)"로 저장하면 UTF-8이 아니라 CP949다. UTF-8로 읽다 실패하면 CP949로 다시 읽는다

**D 주소의 방향은 PlcTwin 표의 표기도 읽는다**
- PlcTwin `device_comments.xlsx`의 방향 열은 "앱→PLC" / "PLC→앱"이다. "입력" / "출력"과 함께 이 표기도 인식한다
