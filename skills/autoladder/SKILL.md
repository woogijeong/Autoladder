# Autoladder

공정 설명과 I/O 할당표를 **프로젝트 파일(JSON)** 로 정리하면, Autoladder가 규칙대로 래더를 만들어 GX Works2용 CSV 2개(`MAIN.csv` 프로그램, `COMMENT.csv` 디바이스 코멘트)로 내보낸다.

네가 할 일은 **프로젝트 파일을 쓰는 것까지**다. 래더 명령(LD, OUT ...)이나 CSV를 직접 쓰지 않는다. 같은 프로젝트 파일이면 결과는 항상 같다.

## 명령

도구는 이 스킬 폴더에 든 `cli.mjs` 한 파일이다(이 SKILL.md와 같은 폴더). Node.js 22 이상만 있으면 되고 설치할 것은 없다. 아래 `<스킬>`은 이 스킬 폴더의 경로로 바꿔 쓴다(보통 `~/.claude/skills/autoladder`, PowerShell에서는 `$HOME\.claude\skills\autoladder`).

```
node <스킬>/cli.mjs check <프로젝트.json>
node <스킬>/cli.mjs generate <프로젝트.json> [--out 폴더]
node <스킬>/cli.mjs diagram <프로젝트.json> [--out 파일.html]
node <스킬>/cli.mjs report <프로젝트.json> [--out 파일.html]
node <스킬>/cli.mjs tags <할당표.xlsx|.csv>
```

- `check`: 검사만. `generate`: 검사 후 CSV를 쓴다(기본 위치는 프로젝트 파일 옆, 파일 이름과 같은 폴더). `tags`: 할당표 파일을 태그 목록 JSON으로 보여 준다.
- `diagram`: 공정 흐름도(단계 = 네모, 단계 이동 = 화살표와 조건)와 운전 설정, 오류·경고를 HTML 한 장으로 쓴다(기본 위치는 프로젝트 파일 옆 `이름.html`). 오류가 있어도 그린다. 쓴 뒤 `Start-Process <파일.html>`로 브라우저에 띄운다. 그림은 인터넷이 있어야 그려진다.
- `report`: 검증 결과서를 HTML 한 장으로 쓴다(기본 위치는 프로젝트 파일 옆 `이름_검증결과서.html`). 자동 검사 18개 항목마다 기준과 판정(합격 / 경고 / 불합격 / 미실시)을 적고, 사람이 GX Works2와 설비에서 확인할 항목을 확인란과 함께 싣는다. 오류가 있어도 쓴다. 사용자가 검증 기록이나 결과서를 원할 때, 또는 `generate` 뒤에 함께 남겨 달라고 할 때 쓴다.
- 종료 코드 0 = 오류 없음, 1 = 오류 있음. 출력의 `오류:` 줄을 읽고 프로젝트 파일을 고쳐 다시 실행한다. `경고:`는 사용자에게 그대로 전한다.
- `node`가 없다고 나오면 사용자에게 Node.js 22 이상 설치를 요청한다.
- 예시 프로젝트 파일: `<스킬>/examples/` (실린더, 신호등, 병렬, 컨베이어 분류, MPS 라인). 처음 쓸 때 비슷한 것을 하나 읽고 따라 쓴다. 프로젝트 파일과 결과물은 스킬 폴더가 아니라 사용자의 작업 폴더에 쓴다.

## 지킬 것

- **사용자가 주지 않은 주소·시간·횟수는 만들지 않는다.** 빠진 값(타이머 시간, 어느 센서로 넘어가는지, 정지 조건, 버튼 주소)은 사용자에게 묻는다. 사용자가 "가정으로 진행"이라고 하면 가정한 값을 따로 적어 알려 준다.
- 공정에 나오는 기기가 할당표에 없으면 임의 주소를 붙이지 말고 사용자에게 주소를 묻는다.
- 운전 설정(시작·정지·비상정지 버튼 등)을 이름에서 추정했다면 적용하기 전에 사용자에게 확인받는다.
- 단계 이름은 한글 4글자 이내가 좋다(디바이스 코멘트 한 행이 8칸, 한글은 2칸).
- 생성 후에는 오류·경고, 가정한 값, CSV 경로를 알리고, **실기 투입 전 GX Works2 시뮬레이터 확인이 필요하다**고 말한다.

## 진행 순서

1. 할당표 정리. 파일(xlsx, csv)이 있으면 `tags` 명령으로 읽거나 프로젝트 파일에 `tagsFile`로 건다. 없으면 대화로 받아 `tags`에 적는다.
2. 공정을 단계로 나눈다. 단계 = "이 출력들이 켜져 있는 상태", 단계 이동 = "이 조건이 되면 다음 단계로".
3. 빠진 값을 묻는다.
4. 프로젝트 파일을 쓰고 `check` → 오류를 고친다.
5. `diagram`으로 흐름도를 띄워 사용자에게 공정이 맞는지 확인받는다. 고칠 곳이 있으면 프로젝트 파일을 고치고 다시 띄운다. **사용자가 맞다고 한 뒤에 `generate`를 한다** (사용자가 그림 없이 바로 만들라고 하면 생략).
6. 결과를 알리고, 사용자가 GX Works2에서 불러온다(프로그램 CSV 읽기 → 변환 → 코멘트 CSV 읽기).

## 프로젝트 파일

```json
{
  "name": "실린더 순차 왕복",
  "tags": [
    { "address": "X0", "name": "시작", "meaning": "버튼" },
    { "address": "X1", "name": "A후진단", "meaning": "센서" },
    { "address": "X2", "name": "A전진단", "meaning": "센서" },
    { "address": "X5", "name": "비상정지", "meaning": "버튼", "contact": "B" },
    { "address": "Y20", "name": "A전진", "meaning": "솔밸브" }
  ],
  "op": { "start": "X0", "estop": "X5" },
  "table": {
    "initial": "a_fwd",
    "steps": [
      { "id": "a_fwd", "name": "A전진", "outputs": ["Y20"] },
      { "id": "hold", "name": "유지", "outputs": ["Y20"], "timer": 2 },
      { "id": "a_back", "name": "A후진" }
    ],
    "transitions": [
      { "from": ["a_fwd"], "to": ["hold"], "cond": { "kind": "input", "address": "X2" } },
      { "from": ["hold"], "to": ["a_back"], "cond": { "kind": "timer", "step": "hold" } },
      { "from": ["a_back"], "to": [], "cond": { "kind": "input", "address": "X1" } }
    ]
  }
}
```

모르는 키를 쓰면 오류가 난다. 아래에 없는 키는 쓰지 않는다.

### tags (할당표)

- `address`: `X`·`Y` + 16진수(`X1F`), 워드의 비트(`D0.F`), 워드(`D144`).
- `name`(필수), `meaning`(생략 가능). 코멘트 1행·2행이 된다.
- `contact`: `"A"`(기본) 또는 `"B"`. B = 평소 ON으로 배선된 입력(비상정지 등). 조건에는 "눌림/감지"로 적으면 접점 방향은 알아서 뒤집힌다.
- `direction`: `"input"` / `"output"`. X·Y는 생략, **D 주소는 필수**.
- 파일로 줄 때는 `tags` 대신 `"tagsFile": "할당표.xlsx"` (프로젝트 파일 기준 상대 경로). 열 제목(주소/이름/의미/접점/방향)으로 열을 찾고, 못 찾으면 `"tagColumns": { "address": 0, "name": 2 }`처럼 열 번호(0부터)를 준다.

### table (단계 표)

- `initial`: 시작 버튼으로 켜지는 첫 단계 id.
- `steps[]`
  - `id`, `name` (필수)
  - `outputs`: 이 단계 동안 켜지는 출력 주소들. 한 출력을 여러 단계에서 써도 된다(이중 코일은 생기지 않는다).
  - `timer`: 단계 타이머(초). 조건에서 `{ "kind": "timer", "step": "id" }`로 쓴다.
  - `timeLimit`: 제한 시간(초). 넘으면 이상 정지.
  - `writes`: 단계 동안 출력 워드에 써 둘 값. `[{ "address": "D144", "value": 50 }]`
  - `calcs`: 단계에 **들어올 때 한 번** 하는 계산. `{ "target": "D10", "left": "D10", "op": "+", "right": 1 }` (op: + - * /), 대입은 `{ "target": "D10", "left": 0 }`. 워드는 `data`에 선언해야 한다. 곱셈·나눗셈은 target 다음 워드도 쓴다(윗자리·나머지).
- `transitions[]` (단계 이동)
  - `from`, `to`: 단계 id 배열. `to: []` = 공정 끝(대기로).
  - 같은 `from`의 전이가 여러 개 = 선택 분기, **위에 적은 것이 우선**.
  - `to`가 여러 개 = 병렬 분기, `from`이 여러 개 = 합류(전부 켜져 있을 때 성립). 병렬 분기는 반드시 합류시킨다.
  - `to`가 첫 단계 = 반복. 반복의 마지막 전이에 `"isCycleEnd": true`를 주면 정지 버튼이 그 자리에서 사이클을 끝낸다.
- `counters[]`: `{ "id": "good", "name": "양품", "countOn": 4, "target": 3, "resetOn": 7 }`. `countOn`·`resetOn`은 transitions의 순번(**0부터**). 조건에서 `{ "kind": "counter", "id": "good" }`.
- `data[]`: 계산·비교에 쓰는 워드 선언. `{ "address": "D10", "name": "개수" }`. 이상 번호 워드(기본 D0)와 겹치면 안 된다.

### cond (조건식)

```
{ "kind": "input", "address": "X2" }                              입력이 눌림/감지
{ "kind": "timer", "step": "hold" }                               그 단계의 타이머 완료
{ "kind": "counter", "id": "good" }                               카운터 목표 도달
{ "kind": "compare", "left": "D10", "op": ">=", "right": 3 }      워드 비교 (= <> > >= < <=)
{ "kind": "not", "cond": { ... } }
{ "kind": "and", "conds": [ ... ] }   { "kind": "or", "conds": [ ... ] }
```

### op (운전 설정). `start`만 필수, 적지 않은 기능은 만들지 않는다

| 키 | 뜻 |
|---|---|
| `start` | 시작 버튼. 대기 상태 + 원위치일 때 첫 단계 시작 |
| `stop` | 정지 버튼. 사이클을 끝내고 대기 (`isCycleEnd` 전이가 있어야 함) |
| `estop` | 비상정지. 모든 단계 해제 + 출력 차단, 풀어도 자동 재시작 없음 |
| `reset` | 이상 해제 버튼 |
| `autoManual` | 자동·수동 스위치. ON = 자동. 없으면 항상 자동 |
| `homeButton`, `homeCondition`, `homeOutputs` | 원점복귀 버튼, 원위치 조건(cond, 시작 조건이기도 함), 복귀 중 켜는 출력 |
| `manual` | 수동 모드에서 누르는 동안만 켜기. `[{ "button": "X7", "output": "Y20" }]` (`autoManual` 필요) |
| `interlocks` | 동시에 켜지면 안 되는 출력 쌍. `[["Y20", "Y21"]]` |
| `sensorPairs` | 동시에 ON이면 이상인 입력 쌍. `[["X8", "X9"]]` |
| `faultLamp` | 이상 램프 출력 |
| `alwaysOn` | 항상 켜 두는 출력 (비상정지·이상 때는 꺼짐) |
| `alwaysWrites` | 항상 써 두는 값. `[{ "address": "D140", "value": 10 }]` |

이상 번호: 제한 시간 초과 = 단계 순번(1부터), 센서 쌍 = 100 + 쌍 순번. 워드 `D{dStart}`에 기록된다.

### devices (내부 디바이스 시작 번호, 생략 가능)

`{ "mStart": 0, "tStart": 0, "cStart": 0, "dStart": 0, "timerTicksPerSecond": 10 }`

- 내부 디바이스(M, T, C, 이상 번호 D)는 시작 번호부터 차례로 자동 할당된다. `check` 출력의 "내부 디바이스" 줄에 무엇이 어디에 잡혔는지 나온다.
- 할당표가 D0 근처를 쓰면(예: PlcTwin의 D0.x) `dStart`를 안 쓰는 번호로 옮긴다.

## 공정의 일부만 만들 때

프로젝트 파일 하나 = 공정 하나 = 프로그램 CSV 하나다. 설비의 한 부분만 원하면 그 부분만 담은 프로젝트 파일을 쓴다(예: `supply.json`, `sort.json`).

- 부분끼리 내부 디바이스가 겹치지 않게 `devices` 시작 번호를 나눈다(예: 공급부 M0~, 분류부 M100~). 각 부분이 쓴 범위는 `check` 출력으로 확인한다.
- 같은 출력을 두 부분에서 켜면 프로그램 사이에 이중 코일이 된다. Autoladder는 파일 하나 안에서만 검사하므로, 부분을 나눌 때 출력이 겹치지 않는지 네가 확인한다.
- 시작·비상정지 같은 운전 설정은 부분마다 따로 적는다.

## 못 하는 것 (요청받으면 사용자에게 알린다)

- 32비트·실수 연산, 아날로그, 계산식 중첩(`D10 = D11 + D12 * 2`는 두 계산으로 나눠 적는다)
- 정전 후 단계 기억, 멈춘 단계부터 다시 시작
- 미쓰비시 Q + GX Works2 외의 기종
- 래더를 한 줄씩 지정해서 쓰기 (단계 표로 표현되는 것만 만든다)
